# Database triggers - none defined in the repository (Part A)

## What is verified

- **No trigger is defined in the repository.** Case-insensitive search for `CREATE [OR ALTER] TRIGGER`, `ALTER TRIGGER`, `ENABLE/DISABLE TRIGGER`, `sys.triggers` and `sp_settriggerorder` over all `*.sql`, `*.cs`, `*.aspx`, `*.config` and `*.md` files (excluding `PrecompiledWeb`, `graphify-out`, generated `docs/` and `specs/`) returned **no trigger DDL and no trigger management statements**. The word "trigger" appears only in ASP.NET/JavaScript UI contexts (`AsyncPostBackTrigger`, "Hidden Trigger" modal control, `.trigger(...)` jQuery/editor code) and in unrelated comments (`INSTEAD OF <tbody>` in GridView helper code).
- The 20 SQL scripts (see `stored-procedures.md`) contain only `ALTER TABLE ... ADD/ALTER COLUMN`, one `CREATE INDEX`, stored procedures, and data fixes. None creates, alters, disables or drops a trigger, and none contains a `DISABLE TRIGGER ... ` wrapper around bulk data fixes (relevant because the fix scripts update `tblInvoice`, `tblDCStore`, `tblOrder` directly - if triggers existed on those tables they would fire; nothing in the scripts accounts for that).
- Therefore whether triggers exist **in the live database** is **UNKNOWN**. Table and SP definitions were not exported to the repository (only ~41 of ~1,000+ SPs), and triggers are stored with the tables.

## Evidence that behaviour is application/SP-driven rather than trigger-driven (CONFIRMED)

The scripts and DAL code write audit/log/derived data **explicitly**, which argues against relying on triggers for these cases:

| Behaviour | Where it is done explicitly |
|---|---|
| Invoice-delete audit | `sp_Delete_ProformaInvoice` inserts `tblInvoiceDeleteLog`, `tblInvoiceDetail_DeleterRecord`, `tblProInvoiceReturnTrack` itself (`sp_Delete_ProformaInvoice_Update.sql:132-163, 200-202`) |
| Stock ledger rows (issue / B2B issue / B2B receive) | inserted by C# (`Library.DAL/SInventory_DAL/ChalanDAL.cs:122-160, 515-545`) and by SPs (`sp_SAP_B2BStockReceiveByDc`); reversal by explicit DELETE (`sp_Del_B2BDelete` v2, `sp_Delete_ProformaInvoice`) |
| `CreateDate/UpdateBy/UpdateDate` on masters | set in the SP bodies (`sp_Save_CustomerMaster`, `sp_Update_CustomerMaster`, `sp_Update_DoctorMaster`) |
| Invoice payment header status | `UPDATE dbo.tblInvoice SET PaymentAmount=..., PaymentStatus=...` in `Library.DAL/SInventory_DAL/CustPaymentDAL.cs:164` (reset in `PaymentReverseDal.cs:52`, `SalesOperationRollbackDAL.cs:654`) |
| Accounts vouchers | inserted by `sp_Sales_CustomerPaymentPosting`, `sp_DeliverySalesReturnPosting`, `sp_SalesReturnPosting` (called from `CustPaymentDAL.PaymentJournalPosting`, `CustomerReturnDAL.PostDeliverySalesReturn`, `ReturnInvoiceDAL.PostSalesReturn`) |
| Return rollback | `Library.DAL/SInventory_DAL/SalesOperationRollbackDAL.cs:313` reproduces "sp_DeleteDeliveryInvoice exact logic" inline in C# (stock adjustment) rather than relying on a database-side cascade |
| Unit-price deactivation | `ProductUnitPriceDAL.MoveUnitPriceToRollback` copies to `tblUnitPriceRollback` then deletes, in one C# transaction (`ProductUnitPriceDAL.cs:219-259`) |

## Places where a trigger *might* be involved (weak / speculative; UNKNOWN)

These are gaps where a derived value is read but no repo code writes it. They are candidates for a hidden writer (an unseen SP, a job, or a trigger) - **not evidence of a trigger**:

1. `tblInvoice.DiscountOnPayment` and `tblInvoice.AIT` are read by `sp_LoadOrderListForOrderCreationbyTerri` (credit/due calculation), `Library.DAL/SInventory_DAL/CreditLimitDAL.cs:91` and `InvoiceDAL.cs:1373-1551`, yet **no INSERT/UPDATE of these two columns** exists in the C# DAL or the 20 scripts (`sp_Sales_CustomerPaymentPosting` only writes vouchers). Their writer is UNKNOWN.
2. `tblCustomerApprovalLog` rows: `sp_Save_CustomerMaster` inserts customers directly approved (`ActionStatus='2'`) and does not write the approval log, while `sp_Get_CustomerApp` LEFT-JOINs the log and treats "no log row" as pending. Who creates the log entries for pending customers (created via app/API) is UNKNOWN.
3. `tblDCStore.ReturnInvoiceDetailId` was added by `Live_Deployment_Script_All_Updates.sql:79-89` but nothing in the scripts or C# writes it (a trigger or an unseen SP could populate it) - or it is simply unused.
4. `tblOrder` snapshot columns (`*_Ord`, `CustomerMasterId`, ...): populated explicitly by `sp_Save_ManualOrderMaster`; the app-created orders (mobile API) are populated elsewhere.
5. Identity-like keys generated by `MAX+1` (`DCStoreId`, `ChalanId`, `ChalanDetailsId`, order numbers) suggest the tables are **not** identity-based and no `INSTEAD OF INSERT` trigger assigns keys - but this cannot be proven from the repo.
